# App Frontend

When the project adopts automatic context maintenance, preserve accepted interaction/API decisions, candidate-bound browser/integration evidence and remaining gaps in its authoritative records and this workstream's checkpoint. A mock or development check does not become production proof.

Inspect the actual application, repository guidance, requested behavior, existing design and service boundaries. Accept adequate contracts and designs from any source; no previous SkillMesh invocation is required.

For material new UX, establish a concrete reviewed direction before expanding production UI. Existing explicit approval or delegated design authority counts. Inspect a representative populated layout at relevant widths in development before repeating its pattern; realistic density and primary actions should expose consequential assumptions early. Production-host proof remains separate. Contained corrections use the established experience. Resolve consequential behavior or contract ambiguity before coding dependent work; continue independent work.

Implement a coherent user journey with real domain copy and meaningful loading, empty, error, success and recovery states. Preserve the reviewed hierarchy, tokens, responsive intent and interaction behavior. Reuse prototype assets/styles when useful and verify framework adaptations visually. Keep semantic structure, keyboard/focus, accessible errors, security and performance active while building.

Follow project terminology and approved copy. Include consequential strings and their state conditions in acceptance checks: labels match actual actions, pending work stays distinct from completion, and shortening preserves validation rules, consequences and supported recovery.

Use the project's suitable components and styling conventions. Prefer mature components for genuinely complex grids/interactions; do not introduce a framework merely because the skill was invoked. Avoid speculative abstractions.

Write for the next person reading the code. Prefer the simplest correct implementation that meets the actual requirements; fewer lines are not an optimization. Apply these choices while implementing and reviewing the changed code:

Use an explicit returning-reader standard: a developer returning to code after six years should be able to follow the business workflow without first decoding clever syntax, hidden conventions or framework machinery. Use modern features when they make the flow clearer; briefly explain necessary unfamiliar mechanisms where used. Avoid both line-by-line tutorial comments and unexplained tricks.

- Make logical blocks visually distinct with blank lines between reading form/state, guards, payload construction, retry decisions, API calls, success updates and failure/recovery handling when present. Keep cohesive assignments together rather than separating every statement. Expand branches, callbacks, calls and object literals into indented lines; do not compress guards, catch or finally bodies onto one line. In templates/JSX, expose element nesting, significant attributes, conditions and events on readable lines, with gaps between meaningful UI sections. Use descriptive names and intermediate values instead of packed expressions or nested ternaries. Follow the formatter but inspect the final source for breathing room; formatter success is not a spacing/readability pass.
- Keep rendering and event flow easy to trace. Use explicit branches for materially different UI states and named handlers for multi-step actions. Prefer straightforward derived values over synchronized duplicate state, unnecessary effects or custom hooks that hide simple local behavior.
- Keep components and functions focused on a coherent responsibility. Extract a component or helper when it gives a meaningful name to complexity, isolates behavior or serves actual reuse. Avoid both sprawling components and fragmentation into trivial wrappers, generic render engines or speculative configuration layers. Reuse established project abstractions when they fit.
- Start with straightforward algorithms and appropriate data structures. Add memoization, caching or other complexity only for a measured bottleneck or concrete performance constraint. Explain the reason locally when the extra machinery would otherwise be surprising; preserve accessibility, state correctness and required performance.
- Before finishing, read the changed code in execution order. Simplify code that requires mentally unpacking several operations, tracing unnecessary indirection or deciphering names. Comments explain intent or a non-obvious constraint; rewrite confusing code rather than narrating it. Keep this cleanup within the requested change.

Keep login, ticket/work-item flows, uploads and administration in coherent components or modules when combining them forces a reader to understand unrelated state. Choose boundaries by responsibility rather than line-count quotas. Prefer typed form/action state and named request/response contracts over generic bags, unexplained assertions or delimiter-encoded selections. Expand templates as well as application code: element nesting, conditions, event handlers and error states should be visible without mentally unpacking a long line. Move consequential template decisions into clearly named logic when it improves tracing, not into generic render/configuration engines.

For material work, trace one representative user action from template and handler through payload construction, API call and success/failure recovery. Show why request identifiers and version tokens are retained or replaced where retries matter. The reader should find the relevant state and steps without navigating a multipurpose component or a chain of trivial wrappers. Report the path reviewed and remaining comprehension obstacles separately from build/test results; owner readability remains unverified until they review it.

Use the real API when available. Otherwise put contract-faithful mocks behind the same service boundary and clearly identify unproved integration. Do not alter API/data/auth rules to make UI coding convenient. Prove real integration when it is part of the requested outcome.

Keep the UI independent of credential storage/provider details. Consume the backend's current-user and allowed-capability contract; do not infer application permissions from unvalidated token contents or assume an external role claim is authoritative. Hidden buttons are not authorization. Preserve denied/expired-session recovery when local login later moves to central identity, without exposing hashes or server secrets to the browser.

For owner-selected IIS hosting, prepare a manual frontend build and deployment recipe: pinned toolchain/dependencies, explicit production build command and output directory, public configuration, API/base-path settings, IIS configuration and operator verification/recovery steps. The owner runs the build, inspects the output and deploys it; do not build release assets, publish, copy to IIS or switch sites without explicit direction. Distinguish static browser output from SSR/server output, which requires a supported runtime. A standalone static site needs its own hosting configuration; assets bundled with ASP.NET Core must preserve the backend's generated web.config and be copied explicitly before the owner's backend publish step, without hidden hooks. Validate SPA fallback, asset loading, cache/version behavior and API authentication against the actual serving topology when the owner-produced artifact is available. Do not assume IIS or separate sites for every project.

Run relevant builds and meaningful tests for logic, state transitions and consequential behavior. For visual changes, render and inspect the affected routes/states at appropriate widths against the reviewed prototype or existing product. Fix drift and retest affected behavior. No browser access means visual proof remains pending.

Exercise one representative real journey using the production bundle and intended serving/security configuration early when integration is material and the artifact is available or its generation is explicitly requested. Release compilation, bundling, publishing and deployment are owner-initiated by default: provide build settings and commands without silently invoking them or adding publish hooks. Ordinary development builds/tests remain implementation verification. If the owner has not produced or authorized the production bundle, report that verification pending and continue independent checks. Development or mock rendering can miss asset, CSP and authentication failures. Preserve useful assertions as project tests; expand coverage with the implementation rather than waiting for final QA to rediscover the boundary.

Present the working journey or affected UI, what changed and why it matters, actual checks, integration mode and remaining gaps. Keep unverified boundaries beside affected claims and durable details in existing project records. Frontend-only scope does not imply backend work or release. Optionally recommend `app-backend`, `app-prototype` or `app-qa` for a specific gap; the agent decides. This skill never invokes another.
