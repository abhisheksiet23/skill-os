# Manual database, backend and frontend release packages

The owner initiates release compilation, publishing, SQL generation and installation. By default prepare the recipe: profiles, explicit build/publish settings, commands, configuration templates and verification/recovery instructions. Do not execute release-producing commands, ZIP/package generation or remote installation without explicit direction. Ordinary development builds/tests are distinct from producing a release. When the owner runs the recipe, artifacts must come from the exact candidate in a clean staging directory. Operator-run scripts can make execution repeatable but must expose inputs, checks, changes and recovery; no hidden remote deployment or startup schema mutation. Keep release-specific facts in the application, not this skill.

## Database handoff

For EF Core use committed migrations and snapshot as schema authority, with reviewed generated SQL for SSMS on SQL Server. Existing non-EF projects keep an adequate versioned migration system. Require a supported starting/ending schema, correct-target preflight, documented SSMS/SQLCMD execution and stop-on-error settings, serialized execution, separate database provisioning, deterministic reference data and post-deployment verification. Migration-history checks do not establish absence of drift. Keep fixture data and credentials out. Initial administrator provisioning is a separate controlled, recoverable identity bootstrap.

Test fresh installation, supported upgrades, rerun and failure behavior against the exact package. Report missing SQL Server/SSMS execution as unverified. Include backup identity/restore evidence, schema/app compatibility and forward recovery when rollback cannot safely restore service. Never substitute a destructive down-migration for an assessed recovery plan.

## Backend handoff

Confirm OS, architecture, hosting model, runtime availability, maintenance window and operator access before choosing a publish target. For .NET provide a Visual Studio Folder publish profile or explicit owner-run `dotnet publish -c Release` instructions, with automatic deployment and database execution disabled. Describe separate restore, build/test, publish, inspection and packaging steps so the owner can inspect outputs before proceeding. Make frontend asset generation explicit where bundled; publishing the API must not silently run frontend or database deployment. The eventual ZIP contains publish output, not bin/obj, source or a development build. Make framework-dependent versus self-contained deployment and runtime identifier explicit. Prefer framework-dependent publishing on a managed IIS server whose supported runtime is maintained; self-contained publishing is an alternative when runtime ownership requires it and brings application-owned runtime patching. Include checksums, build identity, supported schema, configuration template without secrets, prerequisites, install/upgrade steps, smoke checks and recovery steps. Verify the owner-produced published candidate when requested; until then mark package verification pending rather than substituting development serving.

For Windows Server/IIS:

- Establish a dedicated site/application pool, appropriate identity, matching process architecture, supported .NET Hosting Bundle/ASP.NET Core Module, HTTPS binding and correct release-root physical path containing the generated web.config. Verify host-specific prerequisites against current official documentation. Self-contained applications still require the IIS hosting module.
- Keep versioned releases separate from persistent uploads, Data Protection keys, backups, logs and host-owned configuration/secrets. Apply scoped filesystem/SQL permissions. Persist keys under the intended identity; verify decryptability and recovery under that identity, particularly when DPAPI or another host-bound protection mechanism is used. Copying key files alone does not prove they can be restored elsewhere.
- Coordinate database and attachment/file backups so a restore does not leave database records pointing to missing files. Record the recovery point and any reconciliation needed; a database-only restore is not complete application recovery when files live outside it.
- Stage and verify the complete new folder before cutover. In an agreed maintenance window stop/drain the old application and relevant workers, execute the separately reviewed database steps, then switch the IIS physical path to the prepared release and start it. Define the exact stop/start or app_offline procedure; do not overlay files while the process is running. Confirm no other process continues writing during an incompatible migration. Changing IIS path is a controlled cutover, not a promise of zero downtime.
- Smoke-test HTTPS, startup/version, database compatibility, sign-in, a representative authorized operation and relevant upload/download paths. Use designated test data with cleanup; name expected status codes and results. Check logs and background workers. Keep the previous release and record the old path/configuration for recovery; switch back only if it supports the current schema and data.

## Frontend handoff on IIS

The owner explicitly builds the production frontend, reviews its output and manually stages/cuts over IIS. Provide a concise recipe with pinned Node/package-manager versions, locked dependency restore, exact build command, output directory, public environment/API settings, site/base path, configuration files and expected results. Do not execute release builds, publish hooks, file transfers or IIS changes unless explicitly requested. Never embed server secrets in browser bundles or public runtime configuration.

Identify static browser assets versus SSR/server output. A static Angular/React-style frontend can be served by IIS Static Content; an SSR app requires its actual server runtime/hosting setup and cannot be deployed by copying browser files alone. Confirm prerequisites and MIME mappings for the emitted assets; do not infer a .NET Hosting Bundle is needed for an otherwise static-only site.

Choose the topology deliberately:

- For a standalone IIS frontend site/application, provide appropriate web.config and HTTPS/site settings. Specify relative API routing or a reviewed API origin; a separate origin needs matching CORS, cookies/credentials and CSRF behavior, not just a changed URL. Same-origin /api proxying needs an explicit supported proxy configuration; static IIS does not proxy automatically.
- For frontend assets packaged with ASP.NET Core, make the owner's frontend build and copy to a clean web asset staging area explicit before backend folder publishing. Preserve the backend-generated web.config/handler configuration; do not overwrite it with a standalone static-site configuration. The IIS physical path is the backend publish root, not wwwroot. The owner may prefer this single-site arrangement without losing separate control of frontend build and backend publish.

For client-side routing, provide fallback to index.html only for eligible navigation routes. Exclude API paths and real/missing asset requests so API errors and missing JavaScript remain meaningful failures rather than HTML with status 200. Account for IIS application/subpath and base href. Decide whether IIS rewrite rules or the backend owns fallback, avoiding competing handlers. Require URL Rewrite only when the chosen rules depend on that installed module.

Use content-versioned assets and a deliberate index/config cache policy. Consider open browser tabs and lazy-loaded chunks during cutover; retain compatible prior hashed assets or document reload/recovery behavior instead of claiming an atomic folder switch solves browser caching. Include a service-worker update/recovery procedure only when used. Stage a full versioned folder and use controlled cutover rather than overlaying a running site's files. Keep frontend/API compatibility explicit for independent rollback.

Once the owner supplies the built artifact, verify through actual IIS/HTTPS: initial load, deep-link refresh, subpath/assets, missing asset 404, API errors staying API responses, login/session/CSRF, representative read/write behavior and cache/version transition. Inspect rendered screens and console/network errors. Until executed, report IIS/browser verification pending. Keep the prior compatible release, path/configuration and operator recovery steps.

Do not select IIS for another host by habit. Preserve the same artifact, configuration, data, verification and recovery separation using the actual host's equivalent mechanism. No production destination means prepare the recipe and identify the missing environment facts rather than claiming readiness or deployment. Artifact generation remains owner-initiated unless explicitly delegated.

Verify version-specific prerequisites using [Microsoft's IIS hosting guidance](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/iis/) and [EF Core migration deployment guidance](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying).

For frontend serving, consult [Angular deployment guidance](https://angular.dev/tools/cli/deployment) and [IIS static MIME mappings](https://learn.microsoft.com/en-us/iis/configuration/system.webServer/staticContent/mimeMap) when applicable.
