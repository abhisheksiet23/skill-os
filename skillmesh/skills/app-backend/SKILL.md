# App Backend

Work from the actual repository, requested outcome and adequate business/API/data decisions, regardless of who produced them. A frontend, prototype, phase ledger or particular document layout is not a prerequisite for backend work.

Honor adequate technical designs and their cross-component guarantees; resolve routine implementation choices locally. Missing consequential architecture decisions may justify recommending `app-solution-design` with the specific gap, without making a separate design phase mandatory or silently changing accepted decisions.

Identify authoritative boundaries for validation, access and data scope. Implement the required rules, state transitions, calculations and persistence. Keep transport and storage concerns separate when that protects the contract. Make transaction, concurrency, retry, idempotency and partial-failure behavior deliberate where material.

For new applications with local accounts, default to one `Users` table with a single `Role` foreign key, separate `Roles` and `Modules` tables, and `ModuleRoleMapping`; do not add a user-role join table for a single-role requirement. Use the owner's selected bcrypt hashing through a maintained library, keeping credential verification separate from local authorization. Read [simple identity and local authorization](references/identity-and-authorization.md) for schema, credential handling, future central authentication and migration checks. Preserve adequate existing systems until an explicit, data-preserving migration is defined; do not flatten genuine multi-role requirements silently.

Write for the next person reading the code. Prefer the simplest correct implementation that meets the actual requirements; fewer lines are not an optimization. Apply these choices while implementing and reviewing the changed code:

Use an explicit returning-reader standard: a developer returning to code after six years should be able to follow the business workflow without first decoding clever syntax, hidden conventions or the framework's incidental machinery. Preserve modern platform features when they help; explain a necessary unfamiliar mechanism at its point of use. This is a comprehension standard, not a request for tutorials or comments on every line.

- Make logical blocks visually distinct with a blank line between input preparation, guards/validation, queries, business decisions, state mutation, persistence/external effects and response construction when those steps occur. Keep a cohesive assignment group together; do not insert a blank line after every statement. Put early-return bodies and multi-step branches on separate indented lines. Expand dense calls, constructors, records and object initializers so their arguments/properties can be scanned. Give try, catch and finally bodies visible structure using the language's normal brace style. Follow the formatter, but do not assume formatted code has enough breathing room; inspect its final output. Use descriptive domain names and intermediate values rather than compressed expressions; prefer explicit branches or loops over nested ternaries or clever chains.
- Make the normal path, rejection cases and side-effect order easy to trace. Use guard clauses where they reduce nesting, with transaction and resource cleanup intact. Keep authorization, validation, persistence and external effects visible at the relevant boundary rather than hiding them in surprising helpers.
- Keep functions and modules focused on a coherent responsibility. Extract a helper or layer when it names meaningful complexity, protects a real boundary or serves actual reuse. Avoid both sprawling functions and fragmentation into trivial wrappers, one-use generic frameworks or speculative factories and repositories. Reuse established project abstractions when they fit.
- Start with straightforward algorithms, suitable data structures and sensible queries. Do not introduce avoidable repeated queries or unbounded work in the name of simplicity. Add caching, concurrency or other machinery for a measured bottleneck or concrete capacity/latency constraint, and explain the tradeoff when non-obvious. Never simplify away required authorization, transaction, idempotency or failure guarantees.
- Before finishing, read the changed code in execution order. Simplify code that requires mentally unpacking several operations, tracing unnecessary indirection or deciphering names. Comments explain intent or a non-obvious constraint; rewrite confusing code rather than narrating it. Keep this cleanup within the requested change and rerun affected behavioral checks.

Make the public contract and business vocabulary discoverable: prefer names such as `RequireL2Access` and `GetVisibleTickets` over `L2` and `Visible`, and named request/response types at consequential service/API boundaries over anonymous shapes returned as `object`. Use structured values instead of delimiter-encoded fields or positional conventions that callers must reverse-engineer. Local query variables and obvious projections need no ceremonial types or wrappers.

For material work, trace one representative workflow from endpoint through permission checks, validation, state changes, persistence and response. Can the reader identify each step, why its order matters, and what happens on a retry or failure without reconstructing a large multipurpose method? Separate coherent responsibilities where this reduces the reading burden; do not replace a long method with a maze of trivial helpers. Briefly explain approval cycles, concurrency tokens, idempotency or transaction boundaries where their business purpose is otherwise hidden. Report the path reviewed and remaining comprehension obstacles separately from passing tests. Do not claim the owner finds it readable without their feedback.

For uncertain existing-system contracts, prove a thin real integration path before expanding implementation: for example, designated identity through the actual verifier and stored eligibility values to the response. Record exact stored-to-domain mappings. Use read-only access and controlled fixtures where appropriate; passing mocks cannot settle an unverified legacy contract. If the dependency is unavailable, identify the unproved boundary and avoid multiplying work that relies on it.

Inspect consequential queries and data growth. Use versioned, project-appropriate migrations and test existing-data compatibility as well as fresh setup. Keep secrets out of code/logs and make failures diagnosable without leaking private payloads. Use [data and integration](references/data-and-integration.md) for migrations, external effects or coexistence.

For new .NET relational applications, default to EF Core migrations as the schema source of truth and reviewed SQL artifacts manually executed through SSMS for SQL Server. Release compilation, publishing and SQL artifact generation are owner-initiated: provide the settings and commands, and execute only when explicitly requested. Ordinary development builds/tests remain verification, not release publication. Preserve an existing project's adequate migration system rather than introducing a competing schema authority. Read [manual database releases](references/manual-database-releases.md) when creating or changing persistence or preparing database artifacts. Production application startup must not create, migrate or seed the database; use a separately invoked bootstrap for the initial administrator. Other stacks/databases retain native versioned migrations and an appropriate manual SQL client rather than requiring EF or SSMS. Change these defaults only for explicit project requirements or user direction.

Prove rules with meaningful tests and API/data boundaries with appropriate integration checks. Verify delivered endpoints independently, including auth and errors. Reuse the project's request collection or executable API checks; create a Postman collection only when it benefits the actual consumer or project convention.

When a frontend or other consumer is in scope, integrate through the agreed contract and exercise the real boundary. A frontend passing against a mock and a backend passing alone do not establish agreement. No frontend work is required for an API-only task.

For defects, reproduce the behavior, isolate the cause, fix it and rerun the reproduction plus relevant regressions. Resolve material contract changes explicitly rather than silently changing scope. Prove complete increments before multiplying unverified work.

Lead with delivered behavior, why it matters to consumers, consequential choices and supporting evidence. Record actual checks, migration/integration status and limitations beside affected claims in existing project records. Optionally recommend `app-analyze` for missing product decisions or `app-qa` for independent verification, explaining the gap without invoking skills or prescribing phases.
