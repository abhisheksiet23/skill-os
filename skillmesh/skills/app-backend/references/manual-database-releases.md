# Manual database releases

The library default is a prepared release that a human reviews and executes. For new .NET relational projects use EF Core migrations as schema history; for SQL Server deliver SQL for SSMS. Do not retrofit EF into another stack or silently replace an established migration system. Adopting EF on an existing unversioned or custom-versioned database requires a verified baseline against the actual schema, with existing data preserved; never mark a migration applied without establishing equivalence. Keep migration files and model snapshot in source control. Do not edit migrations already applied in shared environments; add a new migration.

Provide owner-run commands to generate schema SQL from the exact application release, with recorded starting and ending migration IDs. Execute SQL generation or other release artifact creation only when explicitly requested; preparing instructions does not authorize compilation or publishing. Prefer a bounded upgrade for a known starting version; an EF idempotent script can cover multiple supported baselines but checks migration history, not arbitrary schema drift. Do not maintain an independently hand-edited schema script alongside generated migrations. Inspect generated SQL when available, especially renames, data movement, nullability, defaults and drops; the generator does not decide whether data loss is acceptable.

Provide a readable package in the application's own release area:

- Operator instructions and a manifest identifying the application candidate, SQL Server compatibility, supported starting/ending schema versions, file order, checksums and expected results.
- Preflight SQL that confirms the intended server/database and migration baseline and detects relevant unsupported state. Keep database creation/provisioning separate from schema transactions; do not infer server paths, recovery model, collation or backup policy without the environment requirements.
- Generated initial-install or upgrade SQL. Document SSMS execution settings and stop-on-error behavior across batches: a bare THROW in one batch must not be assumed to stop later GO batches. Use a tested transaction/error strategy and an execution mechanism that halts on failure, such as explicit SSMS SQLCMD mode with `:ON ERROR EXIT` when appropriate. If SQLCMD features are used, identify and test them and any variable substitution. Serialize deployments using the chosen mechanism; EF-generated SQL is executed outside EF's migration runtime lock.
- Versioned reference-data changes with stable keys and deliberate insert/update behavior. Preserve operator-managed business configuration; exclude test fixtures and credentials. Bootstrap identity through the application's identity components in a separate explicit operation, with recoverable partial-failure behavior and no shared default password. Do not gate all bootstrap recovery merely on whether any user exists.
- Least-privilege permission instructions or scripts, keeping deployment privileges separate from runtime access; read-only verification of objects, history, constraints and required data; backup/restore and failure-recovery instructions.

Ordinary application startup may check schema compatibility and fail clearly, but must not create, migrate or seed production databases. Local fixture tooling must be explicitly limited to development/test environments. Do not package fixtures or bootstrap secrets into the production application ZIP.

Test the exact operator package on an empty database and an upgrade from each supported relevant baseline with representative data. Check rerunning, an incorrect target/baseline, and an injected mid-script failure: no false completion marker or unintended later batch execution. Verify migration history against the intended version and inspect that required data and constraints survive. A generated script or successful compilation is not database deployment evidence. Record unavailable SQL Server/SSMS proof as pending; do not invent passes. Establish backup restore and application compatibility before a consequential change; routing or binary rollback does not undo data changes.

Consult current primary documentation when generating or validating the release: [EF Core migration deployment](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying) and [SQLCMD scripts in SSMS](https://learn.microsoft.com/en-us/ssms/scripting/sqlcmd-scripts-query-editor).
