# Architecture Escalation Triggers

Do not move up the maturity ladder without repeated evidence.

## Improve incrementally

The owner's direction is steady improvement: aim for one small useful addition or improvement each day toward practical perfection. Add missing expertise, refine a method, correct a failure or simplify an unnecessary burden. Use project experience, owner feedback and sound specialist reasoning to choose the next increment; repeated failures are not a prerequisite for a bounded improvement. Preserve working guarantees and verify the affected behavior at an appropriate depth. The stronger evidence requirements below still govern new ecosystem mechanisms.

Practical perfection means reliable handling of intended work with useful expertise, little avoidable ceremony and no known consequential gaps. When no worthwhile increment is apparent, observe use rather than manufacture an addition. Revisit as tasks, tools and observed needs change; keep this learning in existing records rather than creating a daily reporting system.

## Compile inputs into skills

Treat requests, existing instructions, research and observed failures as source material. Recover their intended semantics, reconcile conflicts, then rewrite a coherent instruction set. Do not preserve the source's wording, repetition, chronology or accidental structure merely because it was supplied. Diagnose unresolved contradictions rather than silently changing their meaning.

Optimize within the skill's responsibility: factor shared rules, remove redundant or inapplicable guidance, and place conditional expertise in discoverable owning references. Preserve business logic, accepted choices, authority, safety, exceptions, uncertainty and useful provenance. Handle intended semantic changes explicitly within the user's authorized scope, never under cover of optimization. Neither a shorter skill nor a more elaborate structure proves an improvement.

Distinguish a method's applicability conditions from its firm guarantees. When a heuristic came from one context, preserve the outcome it serves and state when a different approach is appropriate; do not make every task repeat that context's exploration, approvals or artifacts. Keep actual invariants and reserved authority firm. Compare a changed-context case and a settled or invariant case before claiming better transfer; retain adequate existing guidance rather than adding a redundant rule.

Check old-to-new semantic coverage and representative before/after behavior. Keep the compiled instructions and minimal rationale/attribution; discard authoring journeys, copied research and disposable runs. Application facts remain in their own projects.

## Preserve useful detail

Judge instructions by the decisions and outcomes they improve, including avoided errors and rework. Detailed guidance earns its place when it protects an important guarantee or makes execution more reliable. Word counts can help describe loading cost, but are neither a quality score nor a trimming target. Remove redundancy, obsolete advice and irrelevant loading; do not trade correctness or useful expertise for a shorter file. Use representative comparisons for material changes, keeping quality and total effort visible even when provider metrics are unavailable.

## Keep the authoring tree useful

Create a supporting artifact only for a distinct continuing consumer or required deliverable; use an adequate existing record first. Exploring an idea, ranking hypotheses or converting them to use cases does not by itself require files. Keep intermediate reasoning in the conversation or temporary working context, then compile useful conclusions into the owning instructions rather than preserving each authoring stage.

Validation does not automatically require a new permanent task pack, grading key or report. Maintain new evaluation inputs when they add distinct, useful regression coverage; keep one-off inputs and outputs temporary and preserve only decision-driving evidence and limits in the existing checkpoint. Do not move unnecessary artifacts elsewhere merely to keep this tree clean. Preserve required attribution and adopted project records.

Retain maintained skills and references, reusable evaluation tasks/fixtures/keys, active decisions, current evidence limits and required project assessments. Remove disposable run outputs, copied skill variants, generated caches and superseded authoring plans when their useful conclusions are preserved. Use Git history for tracked historical reports rather than retaining every report in the current tree. Before cleanup, inspect callers, repair links and preserve provenance and consequential failures; deleting raw runs does not turn their conclusions into fresh proof. Keep credential/release recovery backups outside routine scratch cleanup.

An explicit owner clean-state reset clears historical run conclusions, scores and verification records from active context as well as raw output. Keep current accepted policy, required source/license attribution and reusable inputs; leave the evidence baseline unestablished. Do not replace deleted history with a new summary of old successes or automatically reload it from Git. Keep only the current checkpoint and latest compact assessment under the project's adopted retention rule. A reset does not erase prior task exposure or authorize rewriting Git history or deleting external recovery backups.

## Add structured handoffs when

Repeated runs show that specialist results are difficult to reuse because key findings, assumptions, evidence gaps, or artifacts are lost in prose.

Start with a small convention, for example:

- findings
- evidence
- assumptions
- open questions
- artifacts

Avoid a mandatory schema until needed.

## Add shared task state when

Repeated long-running tasks show one or more of:

- explicit user decisions are forgotten;
- assumptions mutate into facts;
- multiple specialists create inconsistent context;
- important evidence gets lost between phases;
- the task spans sessions or artifacts and conversation context is insufficient.

If added, keep state curated. Detailed work remains in artifacts.

## Add a capability registry when

Repeated routing failures occur because:

- there are many skills;
- several skills provide similar expertise;
- names/descriptions no longer reliably distinguish providers;
- implementations need to be replaced without changing callers.

Until then, semantic model routing is simpler.

## Add a dynamic runtime when

Model-driven orchestration repeatedly fails even after metadata, instructions, handoffs, and state are improved.

A runtime should solve concrete failures such as deterministic prerequisite enforcement, durable multi-step jobs, concurrency control, or provider selection at large scale.
