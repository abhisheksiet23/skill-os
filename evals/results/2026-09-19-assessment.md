# Initial comparison — 2026-09-19

## What was actually run

Two independent fresh subagents received the same seven bounded requests in `../task-pack.md`, one library catalog each, and the same no-browsing/no-project-mutation constraints. No intended answers or peer results were supplied. Both used the inherited parent model/settings; exact model identity, token usage, latency and complete tool traces were not captured as benchmark metrics. This was one run per variant, with multiple tasks in each run rather than a fresh context per individual case.

The baseline had the original six app and six website skills plus Shipwright's discover skill. The candidate had eighteen SkillMesh skills. Business coverage differs because the new business methods were recovered from the user's conversation during this work; business results are acceptance evidence, not a controlled attribution of gains to shorter wording.

Both evaluators read selected skills and produced actual answers. Both executed the supplied Python function and demonstrated rejection of the valid 100% endpoint plus acceptance of NaN. They did not change project implementation, contact anyone or deploy. All other cases requested plans, calculations, copy or decisions; they are not live application/browser tests.

## Observed outcomes and assessment

| Case | Baseline | SkillMesh | Assessment |
| --- | --- | --- | --- |
| A: standalone review | Concrete executable defects; direct reasoning | Same defects; app-qa used | Both correct; candidate skill loading was not necessary to find this small defect |
| B: existing API/design | Uses actual API and preserves existing design | Same, no phase prerequisite | Both useful; no observed quality gain |
| C: weak pricing evidence | Correct 3,000 contribution after acquisition; bounded options | Same plus explicit metrics, package trade-offs and provisional experiment | Both distinguish assumptions from demand; added business coverage is a confound |
| D: business-to-copy transfer | Exploratory copy, no unsupported guarantees/prices | Same boundaries and useful CTA | Both preserve authority and evidence limits without designing a site |
| E: conflict and stopping | Preserves scope/evidence differences; declines broad scan | Same, with targeted offer comparison | Both resolve the question without a mandatory research chain |
| F: naming | Three names, no skill/research | Same restraint | Both satisfy scope |
| G: stale release proof | Keeps B pending; no deployment | Same; does not re-request staging authority | Both retain the important safeguard |

Using the 0–2 rubric, final-output quality is 2 for both on these bounded cases; context transfer is 2 on D/G; contradiction handling is 2 on E; stopping is 2 on E/F. Candidate selection precision for A is 1 because the same tiny check was solved directly in baseline; no substantive unnecessary skill expansion was observed in the other cases. Discovery is appropriate to each available catalog but not a recall benchmark with an independently established gold set. Composition is partially exercised by carrying business evidence into copy, not by a full multi-skill production task. Dynamic reassessment and human-correction burden are unmeasured; do not assign invented scores.

Baseline read four skill files and nine supporting references; candidate read six skill files and two references. `read-files.json` counts whitespace-separated words in those unique files at inspection, not actual provider tokens or total context. Catalog size, shared instructions, cached reads and task output are excluded. The six SDLC entrypoints total 4,176 source words versus 1,907 SkillMesh words (about 54% shorter), excluding conditional references. This is an instruction-size result, not demonstrated latency/cost savings.

## Packaging and migration proof

- All eighteen skills pass the official skill-creator validator.
- The plugin passes the official plugin-creator validator.
- The local validator finds no missing or cross-skill required references.
- Seven Python packaging regression tests pass.
- Isolated PowerShell migration checks cover exact-name selection across both user roots, no-op inspection, parent/prefix traversal rejection, backup preservation, repeat retirement, restore, restore collision preflight, identity mismatch, a marketplace junction, prepared-source rejection and preservation of the previous release source.
- Independent read-only migration review found marketplace-link and premature-source-displacement defects; both were corrected before profile migration. Native installation is a separate integration check and its outcome belongs in `../../docs/installation-status.md`.

## What remains unproved

No general quality advantage over the originals is established. There is no measured token/cost reduction, real website design comparison, production implementation/migration test, live deployment or longitudinal stopping study. The full business protocol attachments were not recovered. Repeat representative application, browser and business tasks before claiming broader benefit or removing specialized legacy tools.

The next useful evaluation is a real bounded project change using existing project records, measuring artifacts, correction burden and actual loaded context. Additional architecture is not justified by this run.
