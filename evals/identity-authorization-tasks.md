## Raw project exercise

The brief asks for an executable SQLite policy example from business facts, followed by a bounded existing-application handoff. It specifies observable capabilities and a small function interface; it does not prescribe table names, tell the performer to preserve an exception, or supply an expected access matrix. Execute the generated example and its tests. After collection, run [the independent policy checks](fixtures/authorization/check_policy.py) with the generated `policy.py` path, and inspect the selected schema, grant path and existing-application changes. The checker imports generated code; use only the authorized isolated evaluation workspace. Do not give it to performers.

Supplement ordinary cases with withheld combinations derived from the same rules: a second role must not erase another role's valid grant, a read responsibility must not imply approval, a valid grant must not cross a department boundary, and removal/deactivation must affect the next call. Check missing records/actions and policy/database failure. Do not reveal the withheld assertions to performers. Scenarios are reusable regression inputs; publication and prior exposure mean they are not permanently held out. Use fresh project facts for later generalization claims.

## Assess the structure and evidence after collection

- **Consistency:** new-app design, storage, server enforcement and UI capabilities follow the same Users/Roles/Permissions/UserRoles/RolePermissions responsibilities or adequate established equivalents. Record one versus multiple assignments without inventing a second model. Supporting identity, membership and session relations earn their place by behavior; there is no table quota.
- **Access behavior:** current active identity, explicit action grant from an assignment applicable to the target scope, resource membership and workflow conditions all hold. Check read/approve separation, role union, no cross-scope grant composition, direct/list/export paths and current revocation. A schema or a passing policy function does not prove mutation concurrency or complete application integration.
- **Transfer/restraint:** the claims-export case uses its existing policy/search boundary and requires no new local permission store, authentication replacement or database migration. Unknown paging, fields and live contracts remain questions, not guessed behavior or executed passes.
- **Proof quality:** execute the produced example and inspect meaningful negative assertions; distinguish performer tests from independent checks. Report actual files, commands and results. Keep provider/library, SQL Server and production claims outside the SQLite example's proof.

For actual account/authentication changes, retain focused cases for local password verification, multibyte limits and cost rehash; verified external issuer/subject mapping and token trust; SSO-only cookie sessions; and central authorization with an explicitly retained local-password login. For actual migrations, compare effective access and stable IDs/history across old scalar roles, module grants and current assignments rather than rewarding a preferred schema name. Do not combine all cases into every contained change or invent a new evaluation platform.
