## Closed work and retained boundaries

- **T-03/T-07 — verification and authority:** bounded reviews/repairs completed. Use current source and current authorization for new decisions; retired historical checks are not a reason to reopen completed work or a fresh pass. The [standing contracts](product-improvement-use-cases.md#shared-rules) preserve the guarantees without an authorization diary.
- **T-08/T-09/T-10 — one reusable specimen:** retain [ER-1](../evals/equipment-reservations.md), its small shared duration/training policy, existing runner and one conflict/recovery UI. The canonical brief and explicit ER-LIMIT/ER-DRAFT branches remain distinct. Real consumers justify extraction; one useful state does not justify a gallery. Synthetic fixture readiness does not establish application transfer, persistent recovery, usability or field benefit.
- **T-11 — execution before restructuring:** the loading diagnosis led to applying existing scope-first selection and focused retrieval, rather than adding another skill or router. Inspect an actual recurring miss before changing discovery structure. Savings remain unknown.
- **Application learning:** persistence, API access, visible state and the accepted complete journey are separate guarantees. Unit counts do not prove the journey, and old asynchronous responses can invalidate current views. Existing frontend/backend/QA methods already cover much of this; keep application regressions and raw proof in the application. CR-02/03 propose more specific transition triggers, not an assertion that these guarantees were absent.
- **Bundled tooling:** native session/project binding and source search are the default navigation path; portable manifests and host-specific deployment handling have different jobs. A captured chat catalog may need a new chat after authorized rollout. Cold backends may need controlled initialization. Setup mechanics belong in [Serena](serena.md) and [migration](migration.md), not in a second setup checklist here.
- **Tracking:** use metadata-only project-local collection for purposeful operations. Avoid sensitive payloads and double counting; logging must not block useful work. Collection availability is implemented, but low-overhead recurring value and savings remain open. The [tracking contract](use-tracking.md#records-and-limits) owns exact behavior; no dashboard or automatic collector is required.
- **Cleanup and retention:** generated packages, dependency caches and disposable evaluation runs can retire while maintained inputs, accepted decisions, attribution and recovery records remain. Rebuild caches when needed. Update the current view and repair its consumers together; moving an authoring diary elsewhere does not make it useful context.

## Parked choices and attribution

**A2UI:** the owner parked protocol work after the bounded application POC. Retain task-fit component reuse and innovation; do not interpret a known-library preference as protocol adoption, a universal vendor or permission to migrate an application. Revisit for an actual agent-composed interface need, after checking current protocol/renderer/host compatibility and incremental value. Prior assessment sources: [A2UI announcement](https://developers.googleblog.com/a2ui-10-build-delightful-fast-reliable-agentic-experiences/), [MCP Apps guide](https://a2ui.org/guides/a2ui-in-mcp-apps/). These links are provenance, not current compatibility verification.

Keep optional for a concrete recurring query/coordination need and apply [EVOLUTION](../EVOLUTION.md). This is a defer decision, not a missing implementation milestone.

Its ideas informed conditional inquiry and were source material, not agent instructions. Original skill lineage and unrecovered-source limits remain in [source reconciliation](source-review.md). Application evidence stays in its owning project; no deleted run results or scores are reconstructed here.
