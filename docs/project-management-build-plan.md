## Outcome and scope

Deliver a project-owned control view that remains consistent with actual work, plus only the reusable management expertise shown to be necessary. The owner should be able to understand current position, next milestone, blockers, remaining path, forecast assumptions and available cost evidence without rereading chats. A status report alone is a visibility deliverable; optimization requires a decision, action and observed result.

In scope: recover/clarify the delivery boundary, define meaningful completion, reconcile deliverables and dependencies, establish legitimate baselines, maintain actuals and forecasts, manage material risks/issues/changes, communicate exceptions, collect attributable AI/tool-spend evidence, and evaluate corrective actions. Tailor depth to the project; responsibility does not imply a separate document for each activity.

Excluded initially: a PM application/dashboard, custom routing or state runtime, universal project schema, background monitoring, automatic billing integration, formal earned-value reporting without valid inputs, retrospective invented baselines, human labor costing, and automatic changes to global instructions or other projects. New charts or tooling may be justified later by an observed decision/access problem. The unresolved earlier feedback patch is a separate workstream, not a prerequisite and not implicitly accepted, reverted or installed by this plan.

## Ownership and authority

- The owner determines objectives, consequential scope/acceptance commitments, available capacity and spending limits where needed. Existing decisions and delegation carry forward; ask only about a material unresolved choice when it affects the next increment.
- The working agent owns reconciliation, proposed planning, current actuals/forecasts and routine resequencing within existing authority. Specialist implementation/QA records remain authoritative for their underlying evidence.
- Existing project records/tracker own facts. The overview links to their detail rather than becoming a competing source. Name the authoritative source for scope, work state, dates, costs and acceptance when adopting controls.
- Author toolkit methods in `skillmesh/skills/`; run the application pilot in its own project. Use an appropriate authorized application checkout/session. This planning request does not execute the pilot, authorize production actions or grant access to new billing accounts.

## Pilot operating practice

At resumption, check the overview and relevant sources for freshness. After material progress, scope changes or blockers, reconcile affected facts and forecasts. At coherent closeout/handoff, refresh the next path and outstanding decisions. Do not require updates after every tool call or duplicate context assessments with a second session diary.

Preserve baseline, actual and forecast as different concepts. Identify source revision/runtime evidence for acceptance, and retain unresolved claims. Assign risk/issue response ownership. Apply existing decision authority to changes; routine estimates/resequencing do not create a new approval gate. If records disagree, resolve authority/evidence rather than picking the newest timestamp automatically.

For optimization, record the observed constraint, proposed intervention, expected effect, quality/scope guardrails and the result. Candidate measures: time to accepted increment, blocked time where observable, rework/retries, AI/tool spend with coverage, and owner corrections/retrieval burden. Distinguish calendar waiting from active work; do not infer either from a chat's total duration. Compare similar work where possible; a single successful action is a case result, not proof of universal savings.

| Check | Evidence needed |
| --- | --- |
| Actual usefulness | Owner can explain current position, next milestone and decision from the view; compare with prior retrieval/correction burden where observable. |
| Freshness and recovery | A real change/blocker and later recovery preserve current scope, actuals and open decisions. No stale headline is treated as current. |
| Forecast integrity | Missing capacity/blocked dependencies remain explicit; baseline and forecast diverge visibly; no false completion date or percentage. |
| Cost integrity | Duplicate/missing-period inputs, parent/child attribution and subscription allocation do not create false totals. Real pilot access is tested separately from synthetic arithmetic. |
| Management value | At least one real decision is improved or an actionable missing input identified. Optimization requires a corrective action/result; otherwise label the pilot visibility-only. |
| Transfer | Contrasting tasks cover fixed deadline, uncertain scope, parallel work with capacity limits, unavailable billing and trivial work requiring restraint. A replay of only the motivating scenario is insufficient. |
| Source quality | Relevant library/unit/official skill validators pass, or exact unavailability is reported. Synthetic outputs and metadata checks do not count as project-control success. |

## Stop, simplify or expand decisions

- If P1 solves visibility and P4 reveals no missing reasoning, improve existing maintenance rather than expand the library.
- If a cost source is unavailable, preserve financial partiality and address the specific access problem only when useful/authorized. Do not block other project controls or claim cost completion.
- If upkeep exceeds observed decision value, remove duplicate controls and reduce granularity before adding automation.
- If reliable calculations/imports become the repeated bottleneck, consider a bounded helper with provenance and tests, not a general PM runtime.
- If a real optimization opportunity has not occurred, preserve that result and continue honest visibility; do not invent a success to clear a gate.
