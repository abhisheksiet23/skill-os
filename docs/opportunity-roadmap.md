### Benefits review discipline

Choose the opportunity's primary observation and meaningful comparison before implementation, but do not require elaborate instrumentation for a small improvement. Use a relevant existing baseline when valid; otherwise establish an initial observation and state that a comparative movement is not yet known. Record task/source/environment, actual eligible exposure, correction type, quality outcome and available effort/spend using existing records. Count preparation and upkeep when judging economic benefit. Tool/read counts are proxies, not provider billing; self-reported convenience, owner preference, correctness checks and causal savings are different evidence.

An accepted owner preference may justify retaining an inexpensive improvement even when no speed gain is shown. A clear guardrail regression warrants correction immediately. No observed benefit after real exposure calls for reconsidering fit/upkeep, not automatic expansion into a larger catalog. Preserve disconfirming evidence and changed hypotheses. This is Skill OS using its own specialist methods to evolve itself, without making every opportunity run through every method.

## Component libraries and optional agent interfaces

**Observation (2026-11-16):** Google's [A2UI 1.0 announcement](https://developers.googleblog.com/a2ui-10-build-delightful-fast-reliable-agentic-experiences/) describes agent-generated interfaces drawn from registered components. Its [MCP Apps guide](https://a2ui.org/guides/a2ui-in-mcp-apps/) documents bundling a renderer inside an MCP App. Markdown skills alone do not provide that runtime. Protocol, renderer and host versions need separate compatibility checks; the announcement itself lists some integrations still on 0.9.x.

**Owner clarification/direction:** assess applications built using Skill OS. The owner prefers a known component library independently of LLM compatibility and is willing to map use cases to suitable components. Compare that reuse separately from the incremental value of A2UI; a library, selection guidance and a protocol are different choices. The owner authorized an isolated rebuild/comparison in the selected application's own project.

**Owner decision (2026-11-16):** leave A2UI aside after the bounded POC; retain the underlying goals of easier/cheaper LLM work and useful component catalogs. Protect room for innovation rather than restricting applications to prebuilt components. This parks protocol work; it does not authorize deleting the POC or adopting the proposals below.

**Recommendation, not protocol adoption:** use suitable established components and task-based selection guidance. Evaluate A2UI for actual message-driven/agent-composed interfaces; ordinary fixed screens need a demonstrated benefit before adding a protocol. Preserve agent-owned orchestration, independently usable skills and project-owned facts. Catalog schemas describe accepted UI capabilities; use-case mapping explains when to choose them. Neither replaces backend validation or action authority.

**Evidence boundary:** the requested application POC and its component map, runtime checks, measurements, dependency limits and assessment stay in the application's own records. No toolkit-wide A2UI adoption or skill change follows automatically. Engineering productivity, model cost, cross-host portability and general user benefit need their own evidence; source size or one local timing run cannot establish them.

**Brainstorm proposals, not implementation decisions:** improve discovery, comprehension, construction and verification together. Prefer a small existing project map with real entry points/commands, traceable use cases/API types/tests, readable vertical feature boundaries and one representative working example. Provide progressive component discovery: short capability index, task-conditioned selection rules, then version-bound contracts and rendered states on demand. Reuse existing libraries; create domain patterns for actual repeated interactions. Keep reuse, composition, extension and custom invention available without a new approval gate; feed useful proven inventions back into the catalog. Avoid mandatory schemas, giant wrappers, copied vendor documentation and new registries/runtimes without observed need.

**Useful next experiment:** compare ordinary implementation with this focused guidance on one routine change and one interaction poorly served by existing patterns, in an authorized owning app. Measure complete-task effort and verification/correction cost while checking behavior, accessibility and visual quality. Novelty is not an excuse to lose required guarantees; reuse is not a reason to distort a task. Provider-token/cost savings remain unknown unless actually measured. Existing frontend/prototype guidance already covers much of the method; any skill change should address an observed gap rather than duplicate it.

### Hypothesis-validation assessment

Initial assessment, 2026-11-16, followed by owner-authorized execution. Apply the validation method to internal development/adoption decisions, not fictitious market demand. Owner preference establishes direction, not productivity savings. The earlier app POC establishes bounded feasibility, not a component-library-versus-custom authoring comparison. The table and test designs below preserve the initial hypotheses; the execution conclusion follows them.

| Opportunity / falsifiable hypothesis | Current evidence and limit | Learning decision |
| --- | --- | --- |
| Focused project map plus one existing working example reduces rediscovery on unfamiliar bounded changes | Existing policy supports this; reported navigation use suggests uneven application. No measured causal benefit | Test first on a real recurring retrieval difficulty; existing adequate maps are the baseline |
| Clear authoritative behavior/API types and traceable checks reduce incorrect changes and correction cycles | Existing app-consumer/readability methods already require much of this. Comparative benefit unmeasured | Maintain current guarantees; test a specific missing link before adding documentation or refactoring |
| A suitable known component library lowers complete-task effort for routine UI changes | Owner preference and bounded component reuse established; savings versus existing/custom controls unmeasured | Proceed selectively where fit is adequate; measure benefit before requiring a particular library or migrating apps |
| Task-conditioned component mapping improves selection beyond library documentation alone | One app map exists; author/owner use and avoided mistakes unmeasured | Test its incremental value with the library held constant |
| A rendered state gallery prevents meaningful integration/visual defects at lower total effort | Plausible but no comparative result; upkeep may exceed benefit for a few simple controls | Start with a consequential existing pattern/state gap; defer broad gallery construction |
| Further skill splitting/discovery changes reduce irrelevant loading without weakening decisions | Progressive loading already exists; no new repeated routing/loading failure established | Defer structural changes until a trace shows the actual failure; then test semantic preservation |
| Reuse/compose/extend/create guidance preserves task fit on novel work | Explicit owner concern; no observed innovation failure or successful escape-path use yet | Include a real task poorly served by existing patterns in the catalog trial; judge required outcome, not number of custom components |

**First test, discovery:** choose an upcoming unfamiliar change with an observed retrieval obstacle. Compare adequate existing project instructions with a small focused map and one existing example; keep task acceptance, source revision, tools/model configuration and verification equivalent. Measure time/effort to identify the correct change path, wrong paths, corrections and full completion. Record map preparation/upkeep. Proceed only if useful recurring avoided effort can repay that overhead; reshape if discovery improves but completion/rework worsens. A same-agent second attempt has task-exposure bias and cannot establish an independent causal gain.

**Second test, component mapping:** keep the chosen library, component implementations, task facts and existing docs constant; vary selection guidance only. Use one routine UI change and one genuine interaction for which existing patterns fit poorly, with fixed behavioral/accessibility/visual criteria. Measure selection errors, integration fixes, complete-task effort and maintenance of the map. Observe whether the builder extends/creates when warranted and whether the owner can complete the intended task. Both always reusing and always inventing can fail. If this works, separately test the incremental gallery benefit; do not bundle all aids and attribute a gain to one.

**Decision rule and bounds:** define acceptance, eligible task, intervention, measurements and maximum preparation/run effort before each trial, using the actual task's normal delivery budget. Stop at that cap rather than expanding documentation to rescue the hypothesis. No extra paid service, contact or production migration is authorized by this assessment. A numeric cap, recurrence estimate and materiality threshold remain unset until a task is selected; neither test is preregistered or ready to claim a result. Use break-even over a credible reuse horizon: avoided eligible-task effort must exceed setup plus upkeep, with required quality preserved. Record provider tokens/cost only if available; tool counts and retrieved text are proxies, not billing evidence. Missing measurements, inadequate exposure or an untested novel case make the relevant conclusion inconclusive. Initial passes justify a local pilot, not a universal default. Preserve negative findings and changed hypotheses rather than moving thresholds after seeing results.

**Execution conclusion (2026-11-16):** owner-authorized bounded application trials are complete; preregistration, artifacts, candidate-bound acceptance, observed times, interruption/evaluator corrections and assessment remain in the owning application. The trial did not establish cheaper/faster LLM work from the added project/component guidance on a small readable application. Permissive selection guidance coexisted with a new composed domain interaction; this is local feasibility, not a general innovation or usability result. Library-versus-custom authoring cost was not tested because the library was held constant. Preserve the known-library preference, use focused maps only where a real gap warrants them, and defer mandatory catalog schemas, broad galleries and skill machinery. Stop this evaluation rather than expanding tests to rescue a favorable result; reconsider when ordinary work supplies a concrete repeated failure. Provider cost and break-even remain unknown. No toolkit skill/default or production migration was adopted by completing these tests.

**Challenge to proposed follow-up:** prototype/frontend instructions already require suitable component reuse, task fit and room for better interactions. Repeating those rules or creating maps by default would add unproved upkeep. The small prepared codebase and explicit tasks limited room for a selection aid to help; the comparison interaction tests composition, not broad originality. Missing provider-cost measurement prevents an economic verdict in either direction. Strongest counterproposal: retain current methods and, if useful, compile only the owner's established-library preference into one existing paragraph, without treating it as a measured cost improvement or automatic dependency-install rule. Document actual non-obvious decisions at their existing project source; add examples/selection rules when they have a distinct consumer. This is a recommendation, not an accepted skill change. Consistency, accessibility and long-term maintenance remain plausible benefits not tested by the short authoring trial.
