#### Recommended sequence

1. **Verify the operating path and run one bounded CR-09 pilot with CR-06 diagnostics.** Confirm selected models, instruction availability and measurement coverage. Compare one clear worker-sized task against the direct path with equal acceptance. Keep lead supervision, dispatch context, retries, integration and final checks inside the comparison. Do not build a general router or a full benchmark campaign. This first test asks whether the proposed mechanism is economical at all, not whether it fits every task.
2. **Implement the smallest delivery correction: CR-01 + CR-04 + conditional CR-05.** One existing current view should relate the real outcome, domain readiness, current proof and next gap when scope changes. Test both a scope-expansion case and an explicitly requested partial delivery; the latter must still proceed within authority. Do not wait for conclusive token savings to address this known correctness gap. If the pilot stalls, proceed with this correction independently.
3. **Implement CR-02 + CR-03 as an integration safeguard.** Use fixture-to-real-path replacement and a second shared-state entry point as positive cases, plus an unrelated copy edit as the restraint case. Check that the agent selects and executes affected integration checks rather than only writing a caveat. Review implementation drift against accepted architecture before adding mechanisms.
4. **Pilot CR-07 with CR-08 included.** Inspect the actual UI first; choose one observed consequential weakness and compare a representative revision at matched content/state/viewport. Get owner preference feedback alongside functional/accessibility checks. Carry the chosen direction through production and inspect again. Cheap execution may implement settled styling, but retain capable visual judgment. This can proceed alongside step 3 when independent, rather than waiting for all process work to finish.
5. **Promote only supported defaults.** Apply CR-09 model allocations only to task classes with demonstrated benefit; retain selective escalation. Turn CR-06 observations into focused retrieval/rework corrections where evidence warrants them. Defer unproved production-fidelity process, local-provider infrastructure and a broad instruction audit.

These are four bounded increments plus a promotion decision, not nine serial skill invocations. Effort is relatively low for focused instruction compilation and higher for meaningful cost/UI comparison; no measured time or spend estimate is available. The first pilot should stay small enough that its setup does not dominate useful work.

- **Supported starting point:** this chat exposes explicit worker model/reasoning overrides with no-history task dispatch. Local CLI help exposes model selection, profiles and local-provider options. Official documentation supports model/reasoning defaults and custom-agent configuration. These are distinct surfaces: do not assume a CLI setting controls an already-running desktop chat. The bounded pilot below executed worker dispatch; no routing configuration was changed.
- **Proposed allocation:** use a capable everyday lead such as Sol; reserve Astra for consequential ambiguity, difficult diagnosis or design/review where the uplift is worth its cost. Test Luna for bounded extraction, settled-pattern edits and clear repeatable tasks. Select a vision-capable model for screenshot judgment based on demonstrated quality; do not downgrade visual direction simply because the deliverable is CSS. Names are a current starting hypothesis, not a permanent skill-to-model registry. Recheck availability, terms and relative prices when implementing.
- **Dispatch discipline:** delegate only when the work has a clear boundary, adequate input and an observable acceptance check. Give objective, accepted constraints, selected files/sections, permitted write scope, required checks and expected result; avoid passing the whole conversation by default. Include enough cross-component context to prevent local correctness from breaking the journey. A worker returns changed artifacts, actual checks and gaps, not a narrative replay. Lead verifies consequential boundaries rather than reproducing every worker step. For a tiny task, the lead may finish directly if delegation costs more.
- **Escalation:** start at the least costly level supported by task evidence. Missing information needs retrieval, not automatically a stronger model. Escalate when ambiguity, repeated failed attempts or consequential cross-component risk exceeds the worker's demonstrated capability. Retain the reproduction, attempted correction and failing evidence so the next model does not restart discovery. A proposed pilot limit is one failed corrective retry before lead reassessment; stop sooner when the defect risks data or authority. This is a pilot rule, not a universal retry count.
- **Concurrency:** start with one bounded worker and increase only for genuinely independent work when wall-clock improvement justifies extra startup/integration cost. Parallelism is a latency choice, not proof of savings. Preserve existing authorization and file ownership; do not enable autonomous delegation globally through a cost policy.
- **Configuration boundary:** prefer native per-call selection first, then small native defaults/custom-agent files if repeatable benefit is demonstrated. Do not add an API proxy, custom router, new provider, credentials or paid account merely to begin. Third-party/local models are later options for appropriate work after capability, licensing, privacy, hardware and operating cost are established. No user config or paid service was changed here.
- **Acceptance:** compare the current single-model path and mixed-model path on matched bounded implementation, extraction/maintenance, integration-debugging and UI tasks. Keep requirements and checks equivalent; avoid giving one variant the other's solution. Include worker and lead costs, retry/escalation frequency, elapsed time, defects, UI quality and owner rework. Verify actual selected models where observable rather than trusting role names. A cheaper worker that forces the lead to redo the work fails. Subscription allowance observations and API/credit cost are different measurements; never translate the reported five-hour window into a token budget.

**Cost options to test, in order:** (1) native mixed-model execution with bounded handoffs; (2) Standard speed where latency is not valuable; (3) correct reasoning effort per task rather than maximum everywhere; (4) deterministic generation/validation and reuse of verified assets; (5) earlier integration/visual proof to avoid broad rework; (6) local or alternate-provider execution only where measured total cost and quality justify setup. Stable reusable context can aid caching where the surface supports it, but do not assume cache hits, guaranteed discounts or host control over caching. Do not switch to API billing simply to bypass an allowance without a spend boundary.
