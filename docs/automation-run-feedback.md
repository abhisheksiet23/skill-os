## Recommended scenario packet trial

Use a small section in the application's existing authoritative contract/test record. This is a proposed content convention, not a mandatory schema, new skill, shared state service or second source of truth. Application-specific content stays in that project.

- **Source and identity:** scenario ID, requirement/catalogue reference and relevant revision or snapshot. Distinguish the requirement source from the implemented candidate and tested environment.
- **Actors and prerequisites:** initiating user, browser/worker process identity, permissions, supported authentication handoff, controlled data and environment readiness. Reference secret inputs without their values.
- **Ownership and effects:** who may create, view, resume, modify and clean up records; authoritative writer; meaningful retry/concurrency constraints; permitted effects and recovery boundary.
- **Assertions:** observable success, denial and failure behavior; persistence read-back where material; realistic UI states where relevant. Record important conditions that remain unresolved.
- **Scope and dependencies:** minimum platform-enabling work, scenario-specific work and deferred framework features. State which work depends on unproved external behavior.
- **Blockers and evidence:** expected versus observed behavior, candidate/environment, actual command or interaction, result, sanitized evidence link, blocked/untested checks and next useful action.

Keep the proposed completion labels as separate dimensions, not a universal linear ladder:

| Dimension | Meaning |
| --- | --- |
| Implemented | The scoped behavior exists in the identified candidate. |
| Locally verified | Named local checks actually passed; mocks and omissions are explicit. |
| Live verified | The named journey/assertions passed against the intended real dependency and identity in the named environment. This does not imply production deployment. |
| Acceptance | Accepted, unresolved or rejected against the agreed contract; identify whether owner acceptance is required. Technical passes alone cannot resolve an outstanding owner decision. |

Each verification dimension can contain passed, failed, blocked and untested checks. A live failure may coexist with local passes and implemented code. Do not compress mixed results into a green overall status. Source/candidate/environment changes invalidate affected claims, not every check automatically.

Complete the first packet's contract and evidence accounting before expanding dependent framework work. Aim for one real login → controlled draft save → read-back path with the required ownership checks and an inspected representative screen. If the path is blocked, the packet should precisely capture that blocker; it is not accepted or live verified. Continue useful independent work without multiplying assumptions about the blocked boundary. Avoid an absolute rule that all infrastructure must wait: minimum enabling infrastructure is necessary to execute the path.

## Abstraction challenge — 2026-11-03

The earlier recommendation to retain/install the entire patch is now disputed; the narrower proposal below is provisional.

The strongest case for the patch is that concrete instructions can change actions, and the candidate actually probed a failing boundary earlier. The strongest objection is that each feedback item was assigned an edit before establishing whether it revealed a missing principle. Existing skills already covered consequential questions, meaningful increments, early integration, visual review and candidate-bound evidence. More explicit wording can help, but coverage plus one project anecdote does not establish that six additions were necessary.

Project specificity is not limited to names or URLs. Examples and decision gates can preserve a project's workflow even after its nouns are generalized. Conversely, concrete security constraints and realistic UI density are useful specialist knowledge across projects; removing all specificity would weaken the skills. The test is whether the guidance improves a decision across materially different situations without imposing this project's sequence or unnecessary approval burden.
